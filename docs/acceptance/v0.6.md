# v0.6 acceptance foundation

This directory records the test-first contract for the reviewed
implementation specification. The normative input is the unchanged
[`evident-output-spec-adversarially-reviewed.md`](reference/evident-output-spec-adversarially-reviewed.md),
SHA256 `e1f5e03c02cfb07d76a4be859e70bf72b2f46a57c7fb6424daa3bf73d0c5e0df`.
This directory keeps its historical `v0.6` filename, but the shipped
version is **1.0.0** (a breaking release: `MainWith` and `Task.Each` are
removed outright, not deprecated — see the Owner decisions note below).

The future suite (`conformance/future/...`) is deliberately excluded from
ordinary `go test ./...` and from `mise run ci`. Run `mise run
acceptance-v06-green` for the promotion gate that must stay green, and
`mise run acceptance-v06-pending` for the increment-3+ fixtures (Exec) that
are expected to fail to compile until Exec lands.

## Increment 1 — PASSING

Everything below is implemented, green, and covered by both the ordinary
suite (`go test ./...`, `go test -race ./...`, `mise run ci`) and the
`v06acceptance`-tagged future suite's increment-1 packages.

### §1.1 Run/Main/Output.Run context-aware signatures

```go
type RunFunc func(context.Context) error

func Run(ctx context.Context, run RunFunc) Result
func Main(run RunFunc) int
func (o *Output) Run(ctx context.Context, run RunFunc) Result
```

`Result` (`internal/core/result.go`, aliased at `evo.Result`) carries
`Conclusion` plus the application `Err`, with an `ExitCode()` accessor.
`MainWith` (the pre-1.0 `func(*Output) error` form) and its `exitProcess`
facade are removed outright — `internal/engine/run_exit_facade_internal_test.go`
proves `Main` derives its code from `Run` without calling `os.Exit`.

### §7 Define is the scheduling and execution boundary

`TaskHandle.Define(func(context.Context) error)` freezes the Task's
dependency/verification configuration and submits it to the scheduler;
`Define` itself returns immediately after submission. The callback's error
becomes the Task's outcome. `evo.Run`/`evo.Main` wait for every submitted
Task before returning. A second `Define` on the same Task is misuse
(pre-existing `submitWork` guard, unchanged).

Tests: `finish_unresolved_task_amnesty_test.go`,
`internal/engine/verify.go`'s own `runDefine` doc, every `TestScheduler_*`
in `scheduler_test.go`, and increment-1's `conformance/future/api` +
`conformance/future/behavior` packages.

### §4/§5/§6/§48 scheduler (Group, Sequence, After, concurrency)

- `TestScheduler_GroupOverlapRespectsCeiling` — Group siblings overlap;
  `Config.MaxConcurrency` ceiling never exceeded.
- `TestScheduler_SequenceDeclarationOrderMaxOne` — Sequence children start
  in declaration order, never concurrently.
- `TestScheduler_AfterWaitsForPredecessors` — `After` blocks until its
  dependency settles.
- `TestScheduler_GroupSiblingsReportTruthfulIndependentOutcomes` (new) —
  one Group sibling failing does not cascade its siblings to NotStarted
  (that is Sequence's contract); each sibling keeps its own true outcome.
- `sequence_test.go`'s existing suite (unchanged by this increment) already
  covers a failed Sequence predecessor leaving later children NotStarted.

### §3.1 Stable Task/Group/Sequence key — **owner decision: full reversal**

Get-or-create identity for `Task`/`Group`/`Sequence` declaration is removed
outright (1.0.0 breaking change, coordinator-approved): a repeated sibling
name under the same parent is now a duplicate-sibling-name declaration, not
a silent merge into one identity. `internal/engine/identity.go` computes
the default key (`kind:parentKey/normalizedName`) at declaration; a
duplicate declares a real, visible **Failed** task carrying
`ProblemCodeDuplicateSiblingName` (never a panic), so a CLI still gets a
truthful conclusion and exit code, and also records `ErrDuplicateSiblingName`
via the existing misuse channel (`Output.Err()`).

`TaskHandle.Key(key string)` is the advanced override: must be called
before `Define` (`ErrKeyAfterDefine` otherwise); a key already claimed by
another Task of the same kind is `ErrDuplicateKey` (the pre-existing
explicit-key-conflict error, untouched). `Key` is visible on
`TaskSnapshot.Key`/`TasksSnapshot.Key` always (default or override).

Tests: `identity_duplicate_sibling_test.go`, `identity_key_test.go`,
`coverage_matrix_test.go`'s `TestDOM004_SameNameIsDuplicateSibling`,
`last_push_test.go`'s `TestCON018_DuplicateChildNames`,
`sequence_test.go`'s `TestSequence_PackageLevelRepeatIsDuplicateSibling`,
`api_sugar_test.go`'s `TestAPISugar_TaskDuplicateFormattedNameIsRejected`.

**Known narrowing (documented, not silently dropped):** duplicate-sibling
detection is same-kind (Task vs Task, Group vs Group, Sequence vs Sequence)
within one parent, not yet cross-kind (a Task and a Group sharing a name
under the same parent do not collide) — the default key formula already
makes that combination's derived keys distinct (`kind` is part of the key),
so this narrowing is a presentation gap, not a soundness one. Full
cross-kind uniqueness is a reasonable follow-up, out of this increment's
proportional scope.

### §9.1/§9.2 Verify

`TaskHandle.Verify(func(context.Context) (bool, error))` registers an
ANDed pre/post-Define observation check (`internal/engine/verify.go`).
Pre-Define: the Task is already Running; all-true skips Define and resolves
`ResolutionAlreadySatisfied`; any false enters Define; an observation error
fails the Task without entering Define. Post-Define (after a successful
callback): any false fails with `ProblemCodeVerificationUnsatisfied`; an
observation error fails plainly. Neither check commits a success record
alone.

Tests: `conformance/future/behavior/behavior_test.go` (increment-1,
v06acceptance-tagged, passing) — `TestV06VerifyTrueSkipsDefine`,
`TestV06VerifyFalseEntersDefine`, `TestV06VerifyErrorPreventsMutation`,
`TestV06PostVerifyFalseFails`, `TestV06PostVerifyErrorFails`.

### §7.1 Task context

`ErrNoTaskContext`/`ErrTaskClosed` are exported; the unexported
`taskScope(ctx)` accessor (`internal/engine/taskscope.go`) is what File/Exec
(next increment) will use. Directly tested in
`internal/engine/taskscope_internal_test.go`:
`TestTaskScope_NoScopeReturnsErrNoTaskContext`,
`TestTaskScope_InsideCallbackReturnsTheRunningTask`,
`TestTaskScope_AfterCallbackReturnsErrTaskClosed`.

### §29–31 Result/resolution/evidence model

`TaskSnapshot` carries `Resolution` (`executed | already_satisfied |
no_work`, `internal/core/resolution.go`) and `Evidence` (`TaskEvidence`
with `Before`/`After` `EvidencePhase{Evaluated, Satisfied, Source}` —
`Satisfied`/`Source` meaningful only when `Evaluated`). The
before-false/after-true transition is preserved, never collapsed into one
boolean. `Result.ExitCode()` maps OK 0 / Blocked 1 / Failed 2 / Cancelled
130 (pre-existing, unchanged); `Conclusion.ExitCode` and `Result.ExitCode()`
never disagree.

Tests: `result_model_test.go` —
`TestTaskSnapshot_ResolutionNoWorkByDefault`,
`TestTaskSnapshot_ResolutionExecutedWithoutVerify`,
`TestTaskSnapshot_ResolutionAlreadySatisfiedPreservesBeforeEvidence`,
`TestTaskSnapshot_BeforeFalseAfterTruePreservesBothPhases`,
`TestResult_ExitCodeMapping`.

### §46 Public API golden

`api_golden_test.go` + `testdata/api_golden.txt`: an exhaustive, mechanical
listing (via `go/doc`) of every exported type/method/field/func/const/var
in the root package, diffed against the committed golden, plus an explicit
`retiredAPINames` check (`Task.Run`, `Task.Go`, `Task.Each`,
`DisplayGroup`, `Group.Done`, `Sequence.Fail`, `TaskConfig`, `MainWith`)
that fails even if someone regenerated the golden to match. Proven to catch
regressions: temporarily reintroducing a `MainWith` func failed the test
with `retired API name "MainWith" reappeared`.

`dialect_surface_test.go` (a pre-existing, narrower hand-picked-receiver
surface pin) is updated to match: `MainWith`/`Each` removed,
`Define`/`Key`/`Verify` added with their real signatures.

### Owner decisions this increment applied (binding, coordinator-approved)

- 1.0.0, not 0.6 — breaking release.
- `MainWith` and `Task.Each` (`GroupHandle.Each`/`SequenceHandle.Each`)
  removed outright, not deprecated. Examples and conformance goldens that
  used `Each` migrated to plain named Group/Sequence children. Each's own
  **presentation aggregation** (collapsed live/plain rows, the
  cross-child "! skipped N (...)" rollup, the mutation-ledger
  cross-child rollup) was Each-specific rendering
  (`writeLiveEachAggregate`/`writePlainEachAggregate`/`collectEachTaxonomy`/
  `ledgerSubjectFor`'s `fromEach` branch) — removed with it. Restoring an
  aggregated view for large homogeneous groups is renderer work the spec
  itself assigns to a later increment (§4: "aggregation is renderer-owned
  and automatic"), out of this increment's blast radius. Every test that
  pinned that aggregation was either deleted (with an explanatory comment
  naming the regression) or rewritten to assert the per-child shape — none
  were silently weakened.
- §3.1 identity: full reversal (see above), not a narrower fork.
- Duplicate-sibling rejection is a real Failed task with
  `ProblemCodeDuplicateSiblingName`, not a panic, and also feeds the
  existing misuse channel (`ErrDuplicateSiblingName`/`Output.Err()`).

by design (`mise run acceptance-v06-pending` asserts exactly that
failure) — so there is deliberately no single green gate over the whole
`./conformance/future/...` tree; use `mise run acceptance-v06-green` for
the promotion gate.
