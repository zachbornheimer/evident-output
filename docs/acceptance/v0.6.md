# v0.6 acceptance foundation

This directory records the test-first contract for the reviewed
implementation specification. The normative input is the unchanged
[`evident-output-spec-adversarially-reviewed.md`](reference/evident-output-spec-adversarially-reviewed.md),
SHA256 `e1f5e03c02cfb07d76a4be859e70bf72b2f46a57c7fb6424daa3bf73d0c5e0df`.
This directory keeps its historical `v0.6` filename, but the shipped
version is **1.0.0** (a breaking release: `MainWith` and `Task.Each` were removed in 1.0 outright, not deprecated — see the Owner decisions note below).

The future suite (`conformance/future/...`) is deliberately excluded from
ordinary `go test ./...` and from `mise run ci`. Run `mise run
acceptance-v06-green` for the promotion gate — as of increment 3 (Exec),
every package under `conformance/future/...` is implemented and green, so
that target is now `go test -tags v06acceptance ./conformance/future/...`
outright; there is no longer a separate pending/red-by-compile tranche.

## Increment 1 — PASSING

Everything below is implemented, green, and covered by both the ordinary
suite (`go test ./...`, `go test -race ./...`, `mise run ci`) and the
`v06acceptance`-tagged future suite's increment-1 packages.

### §1.1 Run/Main/Output.Run context-aware signatures

```go
type RunFunc func(context.Context) error

func Run(ctx context.Context, run RunFunc) Result
func Main(run RunFunc) int
func (o *Output) Run(ctx context.Context, run RunFunc) Result
```

`Result` (`internal/core/result.go`, aliased at `evo.Result`) carries
`Conclusion` plus the application `Err`, with an `ExitCode()` accessor.
`MainWith` (the pre-1.0 `func(*Output) error` form) and its `exitProcess` facade were removed in 1.0 outright — `internal/engine/run_exit_facade_internal_test.go` proves `Main` derives its code from `Run` without calling `os.Exit`.

### §7 Define is the scheduling and execution boundary

`TaskHandle.Define(func(context.Context) error)` freezes the Task's
dependency/verification configuration and submits it to the scheduler;
`Define` itself returns immediately after submission. The callback's error
becomes the Task's outcome. `evo.Run`/`evo.Main` wait for every submitted
Task before returning. A second `Define` on the same Task is misuse
(pre-existing `submitWork` guard, unchanged).

Tests: `finish_unresolved_task_amnesty_test.go`,
`internal/engine/verify.go`'s own `runDefine` doc, every `TestScheduler_*`
in `scheduler_test.go`, and increment-1's `conformance/future/api` +
`conformance/future/behavior` packages.

### §4/§5/§6/§48 scheduler (Group, Sequence, After, concurrency)

- `TestScheduler_GroupOverlapRespectsCeiling` — Group siblings overlap;
  `Config.MaxConcurrency` ceiling never exceeded.
- `TestScheduler_SequenceDeclarationOrderMaxOne` — Sequence children start
  in declaration order, never concurrently.
- `TestScheduler_AfterWaitsForPredecessors` — `After` blocks until its
  dependency settles.
- `TestScheduler_GroupSiblingsReportTruthfulIndependentOutcomes` (new) —
  one Group sibling failing does not cascade its siblings to NotStarted
  (that is Sequence's contract); each sibling keeps its own true outcome.
- `sequence_test.go`'s existing suite (unchanged by this increment) already
  covers a failed Sequence predecessor leaving later children NotStarted.

### §3.1 Stable Task/Group/Sequence key — **owner decision: full reversal**

Get-or-create identity for `Task`/`Group`/`Sequence` declaration is removed
outright (1.0.0 breaking change, coordinator-approved): a repeated sibling
name under the same parent is now a duplicate-sibling-name declaration, not
a silent merge into one identity. `internal/engine/identity.go` computes
the default key (`kind:parentKey/normalizedName`) at declaration; a
duplicate declares a real, visible **Failed** task carrying
`ProblemCodeDuplicateSiblingName` (never a panic), so a CLI still gets a
truthful conclusion and exit code, and also records `ErrDuplicateSiblingName`
via the existing misuse channel (`Output.Err()`).

`TaskHandle.Key(key string)` is the advanced override: must be called
before `Define` (`ErrKeyAfterDefine` otherwise); a key already claimed by
another Task of the same kind is `ErrDuplicateKey` (the pre-existing
explicit-key-conflict error, untouched). `Key` is visible on
`TaskSnapshot.Key`/`TasksSnapshot.Key` always (default or override).

Tests: `identity_duplicate_sibling_test.go`, `identity_key_test.go`,
`coverage_matrix_test.go`'s `TestDOM004_SameNameIsDuplicateSibling`,
`last_push_test.go`'s `TestCON018_DuplicateChildNames`,
`sequence_test.go`'s `TestSequence_PackageLevelRepeatIsDuplicateSibling`,
`api_sugar_test.go`'s `TestAPISugar_TaskDuplicateFormattedNameIsRejected`.

**Known narrowing (documented, not silently dropped):** duplicate-sibling
detection is same-kind (Task vs Task, Group vs Group, Sequence vs Sequence)
within one parent, not yet cross-kind (a Task and a Group sharing a name
under the same parent do not collide) — the default key formula already
makes that combination's derived keys distinct (`kind` is part of the key),
so this narrowing is a presentation gap, not a soundness one. Full
cross-kind uniqueness is a reasonable follow-up, out of this increment's
proportional scope.

### §9.1/§9.2 Verify

`TaskHandle.Verify(func(context.Context) (bool, error))` registers an
ANDed pre/post-Define observation check (`internal/engine/verify.go`).
Pre-Define: the Task is already Running; all-true skips Define and resolves
`ResolutionAlreadySatisfied`; any false enters Define; an observation error
fails the Task without entering Define. Post-Define (after a successful
callback): any false fails with `ProblemCodeVerificationUnsatisfied`; an
observation error fails plainly. Neither check commits a success record
alone.

Tests: `conformance/future/behavior/behavior_test.go` (increment-1,
v06acceptance-tagged, passing) — `TestV06VerifyTrueSkipsDefine`,
`TestV06VerifyFalseEntersDefine`, `TestV06VerifyErrorPreventsMutation`,
`TestV06PostVerifyFalseFails`, `TestV06PostVerifyErrorFails`.

### §29–31 Result/resolution/evidence model

`TaskSnapshot` carries `Resolution` (`executed | already_satisfied |
no_work`, `internal/core/resolution.go`) and `Evidence` (`TaskEvidence`
with `Before`/`After` `EvidencePhase{Evaluated, Satisfied, Source}` —
`Satisfied`/`Source` meaningful only when `Evaluated`). The
before-false/after-true transition is preserved, never collapsed into one
boolean. `Result.ExitCode()` maps OK 0 / Blocked 1 / Failed 2 / Cancelled
130 (pre-existing, unchanged); `Conclusion.ExitCode` and `Result.ExitCode()`
never disagree.

Tests: `result_model_test.go` —

### Owner decisions this increment applied (binding, coordinator-approved)

- 1.0.0, not 0.6 — breaking release.
- `MainWith` and `Task.Each` (`GroupHandle.Each`/`SequenceHandle.Each`) were removed in 1.0 outright, not deprecated. Examples and conformance goldens that
  used `Each` migrated to plain named Group/Sequence children. Each's own
  **presentation aggregation** (collapsed live/plain rows, the
  cross-child "! skipped N (...)" rollup, the mutation-ledger
  cross-child rollup) was Each-specific rendering
  (`writeLiveEachAggregate`/`writePlainEachAggregate`/`collectEachTaxonomy`/
  `ledgerSubjectFor`'s `fromEach` branch) — removed with it. Restoring an
  aggregated view for large homogeneous groups is renderer work the spec
  itself assigns to a later increment (§4: "aggregation is renderer-owned
  and automatic"), out of this increment's blast radius. Every test that
  pinned that aggregation was either deleted (with an explanatory comment
  naming the regression) or rewritten to assert the per-child shape — none
  were silently weakened.
- §3.1 identity: full reversal (see above), not a narrower fork.
- Duplicate-sibling rejection is a real Failed task with
  `ProblemCodeDuplicateSiblingName`, not a panic, and also feeds the
  existing misuse channel (`ErrDuplicateSiblingName`/`Output.Err()`).

## Increment 4c — §38 structured event stream (JSONL) — PASSING

`internal/wire`'s v2 "evo.event" envelope and family constants landed in
increment 4's render-wire step; this increment wires them to the runtime.
Every required §38 family is emitted from a real lifecycle choke point —
run.started/run.finished (Output construction/Finish, every terminal
path including failure and cancel), collection.declared/task.declared
(Group/Sequence/nested-container/task declaration), task.eligible/
task.started (scheduler dispatch/promotion), definition.started/
definition.finished/evidence.evaluated (Define's Verify-aware wiring),
verification.observed (each registered Verify func), operation.started/
operation.skipped_current/operation.finished/tracked_resource.observed/
basis.fingerprinted (File's and, since the integration merge, Exec's own
reconcile path — `execOperationCurrent` reports the same freshness-reason
vocabulary `fileOperationCurrent` does, plus `no_outputs_declared` for
spec §8.4's "no Outputs → always run" case), effect.planned/
effect.committed (the mutation-verb/File ledger choke point), fact.recorded/
warning.recorded (task- and run-scoped Fact/Warn), and
manifest.task_committed (on a successful CommitTask) — see
`internal/engine/structured_events.go`.

The stream is independent of the legacy 0.3 journal (`internal/core/
event.go`, `internal/render/json.go`, both byte-identical/untouched): its
own `seq` counter, its own vocabulary, and a first-write-failure latch
folded into `Finish`'s misuse error so a mid-stream write failure leaves
every earlier line valid but still fails the Run (spec §32.2) instead of
silently discarding the error.

Required-family distinctions spec §38 calls out are covered by
`internal/engine/structured_events_test.go`:

- whole-Task skip via a satisfied pre-Define Verify vs. entering Define
  because no current proof existed (`TestWireEvents_
AlreadySatisfiedSkipsDefinition` — no definition.started/finished at
  all in the skip case, not just reordered).
- a nested File operation skipped as current (manifest fast path, no live
  inspection) vs. reconciled (`TestWireEvents_FileOperationSkippedCurrent`,
  `TestWireEvents_FileOperationStartedAndFinished`), each carrying a
  distinct freshness reason (`no_prior_record`, `basis_drift`,
  `definition_changed`, `tracked_output_drift`, `current`) —
  `fileOperationCurrent` now reports the reason instead of a bare bool,
  checking Basis ahead of the combined DefinitionFingerprint (which
  already hashes Basis in) so a Basis-only change is never folded into a
  generic "definition changed" verdict.
- run.finished on both a failed and a cancelled run, not only success.
- `seq` strictly increasing with zero duplicates across 40 concurrently
  scheduled tasks, `-race`-clean.
- Exec's own first-run (`operation.started`) and freshness-fast-path
  (`operation.skipped_current`) orderings on the in-package `scriptedRunner`
  fake (`TestWireEvents_ExecOperationStartedAndFinished`,
  `TestWireEvents_ExecOperationSkippedCurrent`), proving the same event
  family File proved above now covers Exec too.

## Increment 3 — PASSING (Exec, freshness graph, capture)

`evo.Exec`/`evo.ExecSpec` (`internal/engine/exec.go`, aliased at the root)
completes spec §8.4's managed-state model alongside File: Exec resolves
Dir (empty/relative against the workspace), Outputs (relative against Dir),
and Executable (PATH lookup for a bare name, resolved against Dir for a
path containing a separator), then fingerprints a definition from the
resolved executable's own content digest, argv, Dir, sorted explicit Env,
sorted Basis, and sorted Outputs (`internal/engine/exec_manifest.go`). A
prior record matching that definition, every Basis digest, and every
declared Output's current on-disk digest skips the spawn entirely; an
ExecSpec with no declared Outputs always runs (nothing observable to skip
by). A successful (exit 0) spawn re-verifies every declared Output exists
and fingerprints, or fails with `ErrExecOutputMissingAfterSuccess`; a
nonzero exit fails with `ErrExecNonzeroExit` and commits no record. Dry-run
never spawns (`internal/engine/exec_test.go`'s
`TestExecDryRunNeverSpawns`); cancelling the Task's context kills the child
(`ProcessRunner`'s contract — the real `exec.CommandContext` does this by
default, and testkit's fake honors ctx.Done() the same way).

Every process spawn goes through the `evo.ProcessRunner` facade
(`Config.ProcessRunner`/`evo.Runner`) instead of `os/exec` directly — the
real `osProcessRunner` in ordinary use, `testkit.ProcessRunner`'s scripted
stdout/stderr/exit/gate fake in tests. Captured stdout/stderr both feed the
Task's existing evidence ring (sanitized, redacted, bounded) and each
completed non-empty line becomes the Task's current Doing activity (spec
§23) via `evidence`'s new `activityFeed` hook — never parsed for totals,
only narrated; a captured secret is redacted before it ever enters the
ring or becomes an activity line.

The freshness graph (`internal/engine/freshness.go`) adds a
producer/consumer barrier without inferring any scheduler edge from a Basis
relationship: claiming a canonical Output (File or Exec) opens a gate the
moment it's claimed — before that operation has actually run — and a later
operation's FSPath Basis on that same canonical path blocks on the gate
until the producing operation settles, then fingerprints whatever is now
on disk. If the producer's freshly written content is byte-identical to
its prior record, the consumer's own definition/Basis/Outputs are
unchanged too, so it stays current — invalidation stops there rather than
cascading. Two operations claiming the same canonical Output in one Run
still conflict at the second claim (spec §8.3/§11.4, `ErrFileConflictingProducer`,
shared with File). A consumer whose own Basis check runs before the
producer has even reached its claim is not reordered by the barrier — spec
§64's explicit narrowing ("no scheduler edge is inferred"); a real pipeline
still declares `After()`/`Sequence` for actual execution order, as
`examples/generate-pipeline` and the `pipeline_test.go` fixtures do.

Tests: `internal/engine/exec_test.go` (skip protocol, output/Basis drift,
nonzero exit, missing output, dry-run, cancellation, captured-line activity,
redaction, the barrier itself, producer conflict), plus
`conformance/future/{api,behavior}/exec` (the v06acceptance-tagged public
contract and behavioral fixtures, including `pipeline_test.go`'s five §64
scenarios: unchanged rerun spawns neither stage; a schema change with an
identical re-normalized output stops invalidation at compile; a schema
change with a genuinely different re-normalized output cascades to
compile; a change scoped to compile's own Basis (`compile.py`) respawns
only compile; and a file unrelated to any Basis/Output disturbs neither).

**Known narrowing (documented, not silently dropped):** simulating "the
running application's own binary changed" (`evo.App()` in Basis) across two
separate `go test` invocations of the same test binary is not practical
within one test process, so that specific §64 sub-case is documented here
rather than exercised as a live assertion; `evo.App()`'s own fingerprint
mechanics are covered by `internal/fingerprint/app_test.go`, and Basis
entries built from it participate in Exec's definition fingerprint exactly
like any other Fingerprint (proven structurally, not by simulating a binary
swap).

As a small increment-2 follow-up in the same file, `evo.File` now also
consults/commits the manifest for a mode-only spec (`Contents` nil,
`Mode` set) — previously only a contents-managed spec did — and skips the
`chmod` syscall entirely when the mode already matches, instead of always
issuing it.
