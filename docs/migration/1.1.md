# Migrating to 1.1

Every breaking change from the 1.0.x line, with the exact before/after code.
If a call site does not appear below, it did not change. 1.1 is a deliberate
breaking release like 1.0 was (no compat shims); see the
[release policy](../../AGENTS.md#release-policy).

## `TaskHandle.Warn`, `Output.Warn`, and `evo.Warn` removed in 1.1 — Problem wins over Warn

Owner vocabulary freeze (2026-09-25): one word per semantic concept. A
warning is a **severity** of `Problem`, not a separate verb, so `Warn` no
longer exists in any of its three shapes. There is no compatibility alias;
every call site must move to `Problem` with `evo.Severity(evo.SeverityWarning)`.

**Before (removed in 1.1):**

```go
func (t *TaskHandle) Warn(summary string) *TaskHandle
func (o *Output) Warn(summary string)
func Warn(summary string)
```

**After (1.1):**

```go
type ProblemSeverity string

const (
    SeverityError   ProblemSeverity = "error"
    SeverityWarning ProblemSeverity = "warning"
)

func Severity(value ProblemSeverity) ProblemOption

func (t *TaskHandle) Problem(summary string, opts ...ProblemOption) *TaskHandle
func (o *Output) Problem(summary string, opts ...ProblemOption)
```

There is no package-level `evo.Problem` function: `Problem` is already the
exported type (`type Problem = core.Problem`), so a same-named function
cannot coexist with it the way the type-free `evo.Warn` once did. A caller
that used the package-level `evo.Warn` on the default instance now calls
`evo.Default().Problem(...)` — `evo.Default()` returns that same default
`*Output` (lazily created), and its `Problem` method is the direct
replacement.

```go
// removed in 1.1 — no longer compiles
task.Warn("stale entry ignored",
    evo.Detail("cache/entry-42.json is 9 days old"),
    evo.Code("CACHE-001"),
    evo.Location("cache/entry-42.json", 0, 0),
)

// 1.1
task.Problem("stale entry ignored",
    evo.Severity(evo.SeverityWarning),
    evo.Detail("cache/entry-42.json is 9 days old"),
    evo.Code("CACHE-001"),
    evo.Location("cache/entry-42.json", 0, 0),
)
```

The package-level form migrates the same way, through `evo.Default()`:

```go
// removed in 1.1 — no longer compiles
evo.Warn("disk nearly full", evo.Detail("92% used"))

// 1.1
evo.Default().Problem("disk nearly full",
    evo.Severity(evo.SeverityWarning),
    evo.Detail("92% used"),
)
```

`Problem` defaults to `SeverityError`: an error Problem fails the owning
Define when the callback otherwise returns nil (ZYS-848 keeps 13-problem
doc P2: "warnings annotate lifecycle; they do not replace it"). A
`Severity(SeverityWarning)` Problem sets `warned` the same way `Warn` did,
and never fails the Define. The MCP review's API-070 rule catches every
remaining `Warn` call spelling and suggests the `Problem` + `Severity`
rewrite mechanically.

`Output.Problem` at the default `SeverityError` records the same run-level
failure `Output.Fail` does — this is intentional, not an accidental second
spelling for the same outcome. `Problem` is the one call that carries a
severity; `Fail` is the terminal-outcome verb kept for a Task's resolution
(`Fail`/`Block`/`Done`/`Skipped`). At the run scope there is no resolution
to choose between, so `Output.Fail` and `Output.Problem(summary)` (default
severity) both express "the run failed," and `Output.Problem(summary,
Severity(SeverityWarning))` is the only way to record a run-scoped warning.
Two spellings converge on one outcome here because `Problem` had to exist
at the run scope for the warning case; a bare error-severity `Output.Problem`
call is simply `Problem` used without its distinguishing option, not a
second warning-verb.

## `TaskHandle.Fact` returns `*TaskHandle`

**Before (1.0):**

```go
func (t *TaskHandle) Fact(name, value string)
```

**After (1.1):**

```go
func (t *TaskHandle) Fact(name, value string) *TaskHandle
```

`Fact` now chains like `Problem` and `Summary`. Call statements compile
unchanged. What breaks is a method value or an interface that spells the
old signature:

```go
// 1.0 — no longer compiles in 1.1
var fact func(string, string) = task.Fact
type facter interface{ Fact(string, string) }

// 1.1
var fact func(string, string) *evo.TaskHandle = task.Fact
type facter interface {
    Fact(string, string) *evo.TaskHandle
}
```

## `TaskHandle.Problem` — a Task can now own many blocking findings, with a severity

New in 1.1, not a rename: `TaskHandle.Problem(summary string, opts
...ProblemOption) *TaskHandle` appends one Problem to the task without
resolving it — call it as many times as the task has findings instead of
creating one `Task` per finding or flattening every finding into one
`errors.New(strings.Join(...))` string:

```go
task := out.Task("check file integrity")
for _, issue := range issues {
    task.Problem(issue.Summary,
        evo.On(issue.Path),
        evo.Code(issue.Code),
        evo.Location(issue.Path, issue.Line, 0),
    )
}
task.Define(func(context.Context) error { return nil })
```

Severity defaults to `SeverityError`. A task holding an error Problem never
settles Done or Skipped: a `nil` `Define` return, a `Skipped` call, or
`Finish` settling the task unresolved all settle it **Failed**. A
`Severity(SeverityWarning)` Problem sets `warned` and never fails the task
(this is the `Warn` replacement — see above). Accumulated blocking evidence
overrides a claimed clean outcome. The task still resolves exactly once;
Problems never become child Tasks. Every accumulated Problem survives in
`Snapshot`/JSON/JSONL even though the plain human view bounds how many
render inline (`maxVisibleProblems`, same bound `Fail`/`Block` already used
for a Detail's evidence lines) — the omitted count still renders as `"and N
more failures"` and the count itself is always authoritative.

## `evo.Exec` returns `(ExecResult, error)` instead of `error`

**Before (1.0):**

```go
task.Define(func(ctx context.Context) error {
    return evo.Exec(ctx, evo.ExecSpec{
        Executable: "golangci-lint",
        Args:       []string{"run", "--out-format", "json"},
    })
})
```

**After (1.1):**

```go
task.Define(func(ctx context.Context) error {
    _, err := evo.Exec(ctx, evo.ExecSpec{
        Executable: "golangci-lint",
        Args:       []string{"run", "--out-format", "json"},
    })
    return err
})
```

Every call site that returned `evo.Exec(...)` directly, or assigned it to a
single `error` variable, now needs the two-value form. An ordinary caller
that never inspects the result ignores it with `_, err := evo.Exec(...)`
exactly as shown above — Exec still owns spawning, capture, liveness,
cancellation, sanitization, and provenance either way; there is no second
raw subprocess API to reach for.

### `ExecResult`

`ExecResult` is the smallest inspection surface for a completed attempt:

```go
type ExecResult struct {
    Ran       bool
    ExitCode  int
    Stdout    string
    Stderr    string
    Truncated bool
}
```

- `Ran` is `false` when Exec skipped spawning entirely — a current manifest
  hit or a dry-run plan — and `true` whenever the child reached a terminal
  exit status, whether that exit was zero, nonzero, or failed output
  verification. It is `false` alongside a spawn/cancellation/configuration
  error, matching `ProcessOutcome`'s own "never produced a terminal exit
  status" semantics.
- `Stdout`/`Stderr` are the capture tail Exec already retains for the row:
  sanitized, redacted, and bounded (at most 200 completed lines, about
  256 KiB total), never a second unbounded copy. `Truncated` reports that
  the bound dropped earlier output. They suit line-oriented diagnostics
  that tolerate a tail; they are not a data channel. When you need a
  tool's complete machine output (a JSON report), have the tool write it
  to a file and read that file.
- A nonzero exit still returns an error wrapping `ErrExecNonzeroExit`, and a
  missing declared Output after a zero exit still wraps
  `ErrExecOutputMissingAfterSuccess` — but now the returned `ExecResult`
  carries the captured attempt too, so a caller that intentionally parses
  nonzero linter output can build a structured finding instead of stopping
  at a flattened error string:

```go
task.Define(func(ctx context.Context) error {
    report := filepath.Join(workDir, "lint.json")
    result, err := evo.Exec(ctx, evo.ExecSpec{
        Executable: "golangci-lint",
        Args:       []string{"run", "--output.json.path", report},
    })
    if !errors.Is(err, evo.ErrExecNonzeroExit) {
        return err // spawn/cancellation failure, or a clean pass
    }
    data, readErr := os.ReadFile(report) // the complete report, not the bounded tail
    if readErr != nil {
        return fmt.Errorf("lint exited %d without a report: %w", result.ExitCode, readErr)
    }
    findings := parseGolangciJSON(data)
    return fmt.Errorf("%d lint finding(s)", len(findings))
})
```

See `ExampleExecResult` in the root package for a runnable version of this
shape.

## `TaskHandle.Define` returns `*TaskHandle`

**Before (1.0):**

```go
func (t *TaskHandle) Define(fn func(context.Context) error)
```

**After (1.1):**

```go
func (t *TaskHandle) Define(fn func(context.Context) error) *TaskHandle
```

`task.Define(fn)` as a statement compiles unchanged. The return value lets
the single-Task shape read `return task.Define(fn).Wait()`; `fn` still runs
on the scheduler, not inline. What breaks is a method value or an interface
that spells the old signature, e.g. `var define func(func(context.Context)
error) = task.Define` or `interface{ Define(func(context.Context) error) }`.
Add the `*TaskHandle` result to that type.

## `After` on a Group or Sequence waits for its members

1.0 treated a Group or Sequence with no Tasks yet as done, so a Task wired
`After` it started at once, before the loop that populates it:

```go
g := out.Group("worktrees")
fetch := out.Task("fetch").After(g) // 1.0: starts now; 1.1: waits for every worktree
for _, path := range paths {
	g.Task(path).Define(remove(path))
}
```

In 1.1:

- A collection that is **empty** when named in `After` (or as the step
  before in a Sequence) stays open. The dependent waits for every child
  declared until `g.Wait()`, a Wait on the dependent, or the end of the
  run closes it. Closed while still empty, it counts as done.
- A collection that is **populated** when named is taken as declared. The
  dependent waits for the children declared so far; a child declared into
  it later never gates that edge.
- A Task declared into a Sequence step after the Sequence moved on to a
  later step runs after the Sequence's latest step, so the Sequence still
  runs one step at a time in declaration order.

What to do:

- If the dependent should wait for the loop's children, no change: wiring
  `After` before the loop now does that.
- If it should start right away, as in 1.0, drop the `After`: an empty
  Group gave it nothing to wait for.
- If it should wait for only the children declared so far, call
  `g.Wait()` first, or declare the children before the `After`.

## `EVO_OUTPUT=json` and `jsonl` write the evo.run document

In 1.0, `EVO_OUTPUT=json` wrote the output.v1 `JSONDocument`
(`schema_version: "0.4"`) and `EVO_OUTPUT=jsonl` wrote 0.4 `EventJSON`
lines at Finish. Neither carried Facts or Kept/Skipped records.

In 1.1, when the program chose no `Format`:

- `EVO_OUTPUT=json` selects `FormatJSON`: one `evo.run` document
  (`schema/run.v2.json`) on stdout at Finish.
- `EVO_OUTPUT=jsonl` selects `FormatJSONL`: `evo.event` lines on stdout as
  they happen, ending with `run.finished`.
- Human output goes to stderr in both.

Each `evo.run` task carries `facts` and `dispositions`, and the event
stream carries `fact.recorded` and `disposition.recorded`.

What to do: parse `object: "evo.run"` / `object: "evo.event"` instead of
the 0.4 shapes. A program that sets `Format: evo.FormatData` (or
`FormatExternal`) keeps stdout for its own payload, so there `EVO_OUTPUT`
still writes the output.v1 projection to stderr.

## Rendering: who decides which rows show

No call site changes. Delete any caller-side workaround for these:

- A `Group` without a `Summary` has no header row in human output. If you
  need a labelled heading, set `Summary` on the Group or use a `Sequence`.
  A failed Group hides its `Summary`, so it loses its header too; a child
  whose name collides with another visible row then shows its Group path
  (`g › build`). Do not rename Tasks to disambiguate them yourself.
- A finished no-op child is hidden when other content is visible (see
  `docs/reference.md`). Do not filter no-op rows yourself.
- `[planned]`/`[changed]` rows follow Task declaration order. Do not sort.
- A cancelled run prints `[cancelled] <subject>  by user` and, only when an
  Effect committed, `! partial changes were applied before cancellation`.
  Remove any `out.Warn("partial changes were applied ...")` you added (`Warn`
  removed in 1.1 regardless); it now prints twice. `! already mutated: ...`
  remains on failed runs only.

## Capture-meaning `Evidence*` names were removed in 1.1

Evidence means one thing in 1.1: proof that requested state is satisfied
(`Verify`, `TaskSnapshot.Evidence`, `EvidencePhase`, `TaskEvidence`). The
retained stdout/stderr/process-output sink is Capture. The capture-meaning
`Evidence*` names below were removed in 1.1, with no aliases.

| 1.0 (removed in 1.1)         | 1.1                         |
| ---------------------------- | --------------------------- |
| `evo.Evidence` (capture)     | `evo.Capture`               |
| `evo.EvidenceOption`         | `evo.CaptureOption`         |
| `evo.EvidenceStream`         | `evo.CaptureStream`         |
| `evo.EvidenceStreamCombined` | `evo.CaptureStreamCombined` |
| `evo.EvidenceStreamStdout`   | `evo.CaptureStreamStdout`   |
| `evo.EvidenceStreamStderr`   | `evo.CaptureStreamStderr`   |
| `evo.MaxEvidenceBytes(n)`    | `evo.MaxCaptureBytes(n)`    |
| `Problem.EvidenceTail`       | `Problem.CaptureTail`       |

`Problem.EvidenceTail` collided with the unrelated proof-meaning
`Problem.Evidence` ([]Attachment) in the same struct; it is now
`Problem.CaptureTail`. The wire JSON key is unchanged
(`"evidence_tail,omitempty"`) — this rename is Go-API-only.

**Before (1.0, removed in 1.1):**

```go
var opts []evo.EvidenceOption = []evo.EvidenceOption{evo.MaxEvidenceBytes(64 << 10)}
stream := evo.EvidenceStreamStderr
```

**After (1.1):**

```go
var opts []evo.CaptureOption = []evo.CaptureOption{evo.MaxCaptureBytes(64 << 10)}
stream := evo.CaptureStreamStderr
```

`KeepLastLines`, `MirrorToDebug`, and `MirrorToDiagnostics` keep their names
and return `CaptureOption`. The ordinary call site does not change:
`cmd.Stdout = task.Writer()` still feeds the Task's capture ring. MCP review
(API-110 through API-116) rewrites every removed spelling.

## Not removed

`ExecSpec` (`Executable`/`Args`/`Dir`/`Env`/`Basis`/`Outputs`),
`ErrExecSpecMissingExecutable`, `ErrExecExecutableNotFound`, and
`ProcessRunner`/`ProcessCommand`/`ProcessOutcome`/`Config.ProcessRunner` are
unchanged. Only `Exec`'s own return arity changed.

## The seven `TaskHandle` mutation verbs and `evo.Affected` were removed in 1.1

`TaskHandle.Add`, `Create`, `Delete`, `Push`, `Remove`, `Update`, and `Write`
were removed in 1.1, along with `evo.Affected` and `evo.MutationOption`.
There are no aliases. Opaque mutations Evo cannot model as desired state (a
Git ref, a worktree, a remote push, an API or database change) use
`evo.Effect` inside `Define`; file state uses `evo.File`.

| Removed in 1.1                             | Replacement inside `Define(func(ctx context.Context) error { ... })`                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `task.Add(object, fn, evo.Affected(n))`    | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectAdd, Object: object, Quantity: n}, fn)`    |
| `task.Create(object, fn, evo.Affected(n))` | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectCreate, Object: object, Quantity: n}, fn)` |
| `task.Delete(object, fn, evo.Affected(n))` | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectDelete, Object: object, Quantity: n}, fn)` |
| `task.Push(object, fn, evo.Affected(n))`   | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectPush, Object: object, Quantity: n}, fn)`   |
| `task.Remove(object, fn, evo.Affected(n))` | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectRemove, Object: object, Quantity: n}, fn)` |
| `task.Update(object, fn, evo.Affected(n))` | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectUpdate, Object: object, Quantity: n}, fn)` |
| `task.Write(path, fn)`                     | `evo.File(ctx, evo.FileSpec{Path: path, Contents: data})` — there is no `EffectWrite`      |
| `evo.Affected(n)` / omitted (meant 1)      | `EffectSpec.Quantity: n` — required, and must be > 0                                       |

**Before (1.0; removed in 1.1):**

```go
task.Delete("worktree", func() error { return removeWorktree(path) }, evo.Affected(1))
task.Write("config.toml", func() error { return os.WriteFile("config.toml", data, 0o644) })
```

**After (1.1):**

```go
task.Define(func(ctx context.Context) error {
	spec := evo.EffectSpec{Verb: evo.EffectDelete, Object: "worktree", Quantity: 1}
	return evo.Effect(ctx, spec, func(ctx context.Context) error { return removeWorktree(ctx, path) })
})
evo.Task("config").Define(func(ctx context.Context) error {
	return evo.File(ctx, evo.FileSpec{Path: "config.toml", Contents: data, Mode: 0o644})
})
```

What stays the same: a dry run records the planned Effect and never invokes
`fn`; an apply run invokes `fn` with the scheduler-owned `ctx` and records
the changed Effect only when `fn` returns nil; a callback that resolves its
own task as `Skipped`/`Fail` records nothing. What changed:

- `Effect` returns an error instead of recording misuse. A zero or negative
  `Quantity`, an empty `Object`, an unknown `Verb`, or a nil `fn` is refused
  (`ErrEffectQuantityNotPositive`, `ErrEffectObjectMissing`,
  `ErrEffectVerbInvalid`, `ErrEffectCallbackMissing`) — return it from
  `Define`. `Affected(0)`'s silent no-op (removed in 1.1) has no equivalent: when there is
  nothing to mutate, do not call `Effect`.
- `Effect` must be called with the `ctx` a `Define` callback received
  (`ErrNoTaskContext` otherwise), so the verb no longer submits the Task by
  itself — `Define` does.
- The unresolved-task hint now reads "call Define, Fail, Block, or Skipped
  on this task".
- An `Effect` callback that committed part of its aggregate before failing
  returns `evo.PartialEffect(committed, err)` (ZYS-972). `Effect` records
  one changed row with `Quantity: committed` (none for 0), then returns an
  error that keeps `err` reachable through `errors.Is`/`errors.As`, so the
  Task fails over a truthful ledger. A nil `err`, a negative `committed`, or
  more than `EffectSpec.Quantity` returns `ErrInvalidPartialEffect` and
  records nothing. Dry runs never call `fn`, so they still plan the full
  `Quantity`. It is not a retry protocol and implies no rollback.

```go
return evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectDelete, Object: "remote ref", Quantity: len(refs)},
	func(ctx context.Context) error {
		committed, err := deleteRefs(ctx, refs)
		if err != nil {
			return evo.PartialEffect(committed, err)
		}
		return nil
	})
```

`evident_output_review` (API-032) rewrites both shapes removed in 1.1 — 1.0's
`Delete(object, fn, evo.Affected(n))` and 0.x's positional `Delete(n,
object)` — to the `Define` + `evo.Effect` form above, and `Write` to
`evo.File`.

## `TaskHandle.Done` was removed in 1.1 (ZYS-812)

`Done` stamped success on a Task whose work evo never saw. There is no alias:
success resolves through `Define` (the callback returning `nil`), and the text
`Done(text)` carried is `Summary(text)` — result metadata that never resolves
the Task (ZYS-971).

| Removed in 1.1                              | Replacement                                                                      |
| ------------------------------------------- | -------------------------------------------------------------------------------- |
| `task.Done()`                               | `task.Define(func(ctx context.Context) error { ...; return nil })`               |
| `task.Done("459 checked")`                  | `task.Summary("459 checked")` inside (or before) that `Define`                   |
| `task.Done("%d checked", n)`                | `task.Summary(fmt.Sprintf("%d checked", n))` — `Summary` takes one string        |
| `task.Done(...)` inside `task`'s own Define | `task.Summary(...)`, or delete a bare `Done()`: returning `nil` already resolves |

**Before (1.0; removed in 1.1):**

```go
branches := evo.Task("branches")
n, err := checkBranches(ctx)
if err != nil {
	return branches.Failf("check branches: %w", err)
}
branches.Done("%d checked", n)
```

**After (1.1):**

```go
branches := evo.Task("branches")
branches.Define(func(ctx context.Context) error {
	n, err := checkBranches(ctx)
	if err != nil {
		return err
	}
	branches.Summary(fmt.Sprintf("%d checked", n))
	return nil
})
```

A Task with nothing to do is not a `Done` row either: when a precondition
already holds, `Verify` returns `true` and the Task resolves
`ResolutionAlreadySatisfied` without running `Define`'s callback. Keep
`Summary` for the caller's own result (a count, a verdict); mutation,
dry-run, and already-satisfied narration belongs to `Effect`/`File`,
`Verify`, and `Fact` (API-060 flags it).

`evident_output_review` (API-032) rewrites every `Done` call site to the
`Define`/`Summary` form above for a 1.1 target; a 1.0 pin is not flagged.

## `evo.ID`, `evo.StartPhase`, and `evo.EntityOption` were removed in 1.1

`Task` takes only a name, so no API accepted an `EntityOption`: `evo.ID` and
`evo.StartPhase` built values nothing consumed. They are gone, with no
aliases.

| Removed in 1.1                                 | Replacement                                  |
| ---------------------------------------------- | -------------------------------------------- |
| `evo.ID("build.base")` (stable identity)       | `task.Key("build.base")` before `Define`     |
| `evo.StartPhase("resolving tag")` (first step) | `evo.Task("pull").Doing("resolving tag")`    |
| `evo.EntityOption` (the type)                  | none: nothing takes a declaration option now |

`evident_output_review` (API-032) rewrites both call shapes.

## `EffectInstall` and `EffectUninstall` (ZYS-974)

The `EffectVerb` enum grows two package-lifecycle verbs alongside `Add`,
`Create`, `Delete`, `Push`, `Remove`, and `Update`:

```go
const (
    EffectAdd       EffectVerb = "add"
    EffectCreate    EffectVerb = "create"
    EffectDelete    EffectVerb = "delete"
    EffectInstall   EffectVerb = "install"
    EffectPush      EffectVerb = "push"
    EffectRemove    EffectVerb = "remove"
    EffectUninstall EffectVerb = "uninstall"
    EffectUpdate    EffectVerb = "update"
)
```

`installed N packages` / `uninstalled N packages` are materially clearer CLI
truth than forcing package lifecycle into generic `add`/`remove` wording, so
they are first-class verbs, not a free-text extension point — there is still
no free-text `EffectVerb` and no `EffectWrite`. Tense is automatic: `[planned]`
rows keep the imperative (`install`/`uninstall`), `[changed]` rows conjugate
past tense (`installed`/`uninstalled`) the same way every other verb does.

```go
task.Define(func(ctx context.Context) error {
    return evo.Effect(ctx, evo.EffectSpec{
        Verb: evo.EffectInstall, Object: "package", Quantity: n,
    }, install)
})
```

### `Record`/`RecordLabel`/`RecordName` were removed with no record-only replacement

`Record`, `RecordLabel`, and `RecordName` were removed in 1.1 (ZYS-812).
There is no alias and no record-only replacement; migrate each call site by
what it reports. Every left-hand shape below was removed in 1.1:

| Call site shape                                                                                                              | Replacement                                                                                                                                                                |
| ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A real mutation reported after the fact (`task.Record("delete", n, "worktree")` next to code that already deleted worktrees) | Move the mutation itself inside `evo.Effect(ctx, evo.EffectSpec{...}, fn)` so dry-run and committed truth stay structural — do not report a mutation that already happened |
| An install/uninstall-shaped mutation (`task.RecordName("install", pkg)`, `task.Record("uninstall", n, "package")`)           | `evo.Effect(ctx, evo.EffectSpec{Verb: evo.EffectInstall /* or EffectUninstall */, Object: "package", Quantity: n}, install)`                                               |
| Information learned, not a mutation (`task.RecordLabel("reused", n, "cached package")`)                                      | `task.Fact("reused", strconv.Itoa(n))` — or a `Problem`/taxonomy call when it is a finding, not a count                                                                    |
| A file-looking write (`task.RecordName("write", path)`)                                                                      | `evo.File(ctx, evo.FileSpec{...})`, or `set, err := evo.Patch(ctx, diff)` then `evo.Files(ctx, set)` — never `Effect` for file state                                       |
| Post-hoc mutation reporting from a hook/autofix step                                                                         | Move the report to the operation that actually commits the change; do not add a new record-only call site                                                                  |

`evident_output_review` treats `evo.Effect`'s callback doing no real work as
API-042 ("the mutation already ran elsewhere") and no longer suggests
`task.Record` as the fix — the fix is to move the mutation inside the
callback.

`evident_output_review` (API-061) flags every remaining `Record`/
`RecordLabel`/`RecordName` call and spells the exact replacement for its
shape: the matching `EffectVerb` for a verb literal, `evo.File` for
`"write"`, and `Fact` for `RecordLabel`.
