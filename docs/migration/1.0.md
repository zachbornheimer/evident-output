# Migrating to 1.0

Every breaking change from the 0.5.x line, with the exact before/after code.
If a call site does not appear below, it did not change.

## `Run` / `Main` / `Output.Run` now take and derive a `context.Context`

**Before (0.5):**

```go
func main() {
    evo.Init(evo.Config{Title: "ghost"})
    os.Exit(evo.Main(run))
}

func run() error {
    evo.Task("working tree").Done()
    return nil
}
```

**After (1.0):**

```go
func main() {
    evo.Init(evo.Config{Title: "ghost"})
    os.Exit(evo.Main(run))
}

func run(ctx context.Context) error {
    evo.Task("working tree").Done()
    return nil
}
```

`type RunFunc = func(context.Context) error`. `evo.Main(run RunFunc) int` still
owns SIGINT/SIGTERM-to-Cancel wiring and still never calls `os.Exit` itself —
only the signature of `run` changed, so it can carry cancellation into a
`Define` callback or a child process. `evo.Run(ctx, run) Result` and
`(*Output).Run(ctx, run) Result` take the caller's own `context.Context`
directly instead of deriving one internally, for a caller composing its own
cancellation.

## `Run` / `Main` / `Output.Run` return `Result`, not a bare exit code

**Before (0.5):** `evo.Run(run)` returned `int` — just the exit code.

**After (1.0):**

```go
type Result struct {
    Conclusion Conclusion
    Err        error // the application error run returned, if any
}

func (r Result) ExitCode() int { return r.Conclusion.ExitCode }
```

`evo.Run(ctx, run) Result` and `(*Output).Run(ctx, run) Result` return the
full `Result` — the finished `Conclusion` plus the application error `run`
returned — so a caller that needs both no longer has to re-derive the error
from side state. A caller that only wants the code keeps calling
`.ExitCode()`:

```go
// Before
code := evo.Run(run)

// After
result := evo.Run(ctx, run)
code := result.ExitCode()
```

`evo.Main(run RunFunc) int` is unchanged in this respect — it still returns
only the derived `int` exit code, because `os.Exit` only ever wants a code.

## `evo.MainWith` was removed in 1.0

**Before (0.5):** an `Isolated *Output` exited the process through
`evo.MainWith`:

```go
out := evo.Init(evo.Config{Isolated: true})
os.Exit(evo.MainWith(out, run))
```

**After (1.0):** an `Isolated *Output` calls its own `Output.Run` and maps
the result itself — there is no longer a second facade that restates the
same `os.Exit` shape for a hosted instance:

```go
out := evo.Init(evo.Config{Isolated: true})
os.Exit(out.Run(ctx, run).ExitCode())
```

Ordinary `main()` still uses `evo.Main` unchanged.

## `Task.Each` / `Group.Each` / `Sequence.Each` were removed in 1.0

**Before (0.5):**

```go
evo.Group("install").Each(packages, func(pkg string) error { // removed in 1.0
    return install(pkg)
})
```

**After (1.0):** declare one named child `Task` per item directly, then
`Define` submits that item's work:

```go
installs := evo.Group("install")
for _, pkg := range packages {
    pkg := pkg
    installs.Task(pkg).Define(func(ctx context.Context) error {
        return install(pkg)
    })
}
```

`evo.Sequence` takes the identical shape for ordered work. This is not a
get-or-create loop helper: declaring the same child name twice under one
parent is a duplicate sibling declaration (see below), not a merge.

## `Define` is the scheduling and execution boundary

**Before (0.5):** a mutation verb (`Add`/`Delete`/`Create`/…) or `Define`
both submitted work to the scheduler with no distinction in how freshness
was decided.

**After (1.0):** `Task.Define(fn func(context.Context) error)` is the one
call that submits a Task's callback to the scheduler (§7). Mutation verbs
are unchanged and still submit their own callback the same way. What is new
is `Verify` running _before_ `Define` (see below) to decide whether `Define`
runs at all — `Define` itself never re-checks; it is purely "the work,"
executed when nothing has already proven it unnecessary.

## `Task.Verify` — the boolean pre-Define check

**New in 1.0.** `Task.Verify(fn func(context.Context) (bool, error)) *TaskHandle`
registers a read-only check that runs before `Define`. `fn` returning
`(true, nil)` means the desired state already holds: Evo skips `Define`
entirely and resolves the Task `ResolutionAlreadySatisfied`. `fn` returning
`(false, nil)` runs `Define` as normal.

```go
task := evo.Task("already-configured")
task.Verify(func(ctx context.Context) (bool, error) {
    return configAlreadyWritten(path)
})
task.Define(func(ctx context.Context) error {
    return writeConfig(path)
})
```

Teach `Verify` only for domains Evo cannot track automatically — `evo.File`
and `evo.Exec` already derive their own freshness and do not need one.
`Verify` controls whole-Task fast skipping; it is not the same claim as an
operation-level `Basis` (see Fingerprint, below) — see spec §56 for the
full distinction.

`TaskConfig` (a proposed Task-construction struct) is removed in 1.0 and
will not return: Task authoring stays fluent (`task.After(x); task.Define(fn)`),
matching the rest of the entity API. Structs remain the right shape for
_data_ — `FileSpec`, the persisted manifest, wire payloads — never for Task
construction itself.

## `Task.Key` — stable identity independent of the display name

**New in 1.0.** `Task.Key(key string) *TaskHandle` overrides a Task's
tracked identity (spec §3.1) when its display name is expected to change
across runs (a version number, a path) but its persisted evidence must
still resolve to the same tracked entity:

```go
evo.Task("migrate 003_add_users.sql").Key("migration:003").Done()
```

Without an explicit `Key`, a Task's stable identity is derived from its
name and position in the declaration tree.

## Duplicate sibling names are not a get-or-create

**Before (0.5):** calling `evo.Task("branches")` twice with the same name at
the same call site was sometimes used as an implicit lookup for "the branches
task, whichever one already exists."

**After (1.0):** every declaration is a new sibling. Two `Task` calls with
the same name under the same parent produce two distinct `*TaskHandle`
values and record `ErrDuplicateSiblingName` on the owning `*Output` — the
handle you got back is the one you keep using:

```go
// Before (relied on repeated calls resolving to the same task)
evo.Task("branches").Doing("scanning")
// ... later ...
evo.Task("branches").Done()

// After — keep the handle
branches := evo.Task("branches")
branches.Doing("scanning")
// ... later ...
branches.Done()
```

## `evo.File` — declarative managed-state file operations

**New in 1.0** (spec §8). Replaces a hand-written "read, compare, write"
`Define` callback with one declarative call:

```go
task.Define(func(ctx context.Context) error {
    return evo.File(ctx, evo.FileSpec{
        Path:     path,
        Contents: contents,
        Mode:     0o644,
        Basis:    []evo.Fingerprint{evo.FSPath("template.tmpl")},
    })
})
```

`FileSpec.Contents == nil` means contents are unmanaged (mode-only);
`Basis` lists additional `Fingerprint` inputs whose change invalidates the
prior record even when `Contents`/`Mode` alone look unchanged. `ctx` must
come from a Task's `Define` callback — called any other way, `File` returns
`ErrNoTaskContext`/`ErrTaskClosed`. Do not teach a hand-rolled Evidence
callback as the default way to make file work idempotent; reach for `File`
first.

## `evo.Fingerprint` / `evo.FSPath` / `evo.Value` / `evo.App`

**New in 1.0** (spec §11.1). A `Fingerprint` observes one `Basis` input's
current content identity without mutating anything:

| Constructor          | Fingerprints                                                           |
| -------------------- | ---------------------------------------------------------------------- |
| `evo.FSPath(path)`   | A file's byte digest, a directory's Merkle digest, or a symlink target |
| `evo.Value(name, v)` | A caller-supplied scalar under a stable, non-secret name               |
| `evo.App()`          | The running application's own implementation identity                  |

Use these to build a `Basis` slice for `FileSpec.Basis` (and, once `Exec`
lands, `ExecSpec.Basis`) — never invent a `Basis` entry the source code does
not actually read.

## `Format` gained machine-projection values

**Before (0.5):** `Format` selected `FormatHuman` or `FormatData` only.

**After (1.0):** `Format` is unchanged (`FormatHuman`/`FormatData`/
`FormatExternal` still only route streams), but `Config.Projection` /
`EVO_OUTPUT` gained explicit machine encodings alongside human/plain:

```go
const (
    ProjectionHuman      // TTY/plain inference (default)
    ProjectionPlain      // durable report, no live region
    ProjectionJSON        // one JSONDocument at Finish
    ProjectionJSONL        // Event JSON Lines at Finish
    ProjectionStreamJSON  // one EventJSON line per journal append
)
```

`EVO_OUTPUT=human|plain|json|jsonl|stream-json` (`stream_json` also
accepted) selects `Projection` when the matching `Config` field is unset.
Teach output format and verbosity once at the application boundary — never
per Task.

## `Result` / exit-code mapping

`Result.ExitCode()` is `Result.Conclusion.ExitCode` — unchanged mapping from
0.5's Conclusion table:

| Band                                  | Exit code |
| ------------------------------------- | --------- |
| `[changed]` / `[planned]` / `[ready]` | `0`       |
| `[blocked]`                           | `1`       |
| `[failed]`                            | `2`       |
| `[cancelled]`                         | `130`     |

What changed is only _how_ a caller reaches the code: through
`Result.ExitCode()` (from `evo.Run`/`Output.Run`) instead of a bare `int`,
or through `evo.Main`'s still-bare `int` return for the ordinary CLI case.
Never hand-map an int to `os.Exit` — that is exactly how a Blocked run (`1`)
gets silently read as success, or a real failure reads as blocked.

## Not removed

Mutation verbs (`Add`/`Delete`/`Create`/`Update`/`Remove`/`Write`/`Push`),
`Task.Skipped`/`Task.Kept`, `Record`/`RecordName`/`RecordLabel`,
`evo.Confirm`, and the severity dialect (`Warn`/`Block`/`Fail`) are
unchanged. If you are not calling `MainWith` (removed in 1.0) or `.Each(`
(removed in 1.0), most call sites need no edit beyond adding
`ctx context.Context` to your `run` function.
